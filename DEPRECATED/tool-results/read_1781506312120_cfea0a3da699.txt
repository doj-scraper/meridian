     9→## Executive Summary
    10→
    11→Agent Studio OS V1 established a solid foundation: visual canvas, single-agent execution with Plan→Execute→Evaluate, SSE streaming, kill switch, and an AI Builder wizard. V2 transforms this from a **task-orchestration UI** into a full **Agent Runtime OS** — a platform where specialized agents collaborate through structured orchestration patterns, govern themselves with policies, persist knowledge across runs, and operate within verifiable safety boundaries.
    12→
    13→The upgrade is organized into **4 phases** across **12 major workstreams**, informed by current research on multi-agent orchestration (AutoGen), the Evaluator-Optimizer reflection pattern, OS-level resource management (AgentCgroup), and production-grade security (SEAgent).

    89→## Phase 1: Multi-Agent Orchestration Engine (Core V2)
    90→
    91→*This is the centerpiece of V2 — transforming from single-agent execution to multi-agent collaboration.*
    92→
    93→### 1.1 — Orchestration Mode Engine
    94→
    95→**Research basis:** AutoGen defines 3 core patterns — Sequential Pipeline, Group Chat, and Hierarchical Chat. Our V2 plan adds Parallel as a fourth mode.
    96→
    97→**Implementation:**
    98→
    99→```
   100→OrchestrationMode = 'single' | 'sequential' | 'group' | 'hierarchical' | 'parallel'
   101→```
   102→
   103→| Mode | Description | Best For |
   104→|------|-------------|----------|
   105→| `single` | Current V1 behavior — one agent loops | Simple tasks, backward compat |
   106→| `sequential` | Pipeline A→B→C with output handoff | Content workflows, ETL |
   107→| `group` | Shared scratchpad, turn-taking manager | Deliberation, writer-editor-reviewer |
   108→| `hierarchical` | Manager delegates to sub-agents | Complex projects with sub-tasking |
   109→| `parallel` | Fan-out to N agents simultaneously | Speed-optimized research |
   110→
   111→**Database changes:**
   112→```prisma
   113→model Agent {
   114→  // ... existing fields
   115→  orchestrationMode  String   @default("single")   // single|sequential|group|hierarchical|parallel
   116→  maxConcurrency     Int      @default(3)           // for parallel mode
   117→  teamId             String?                        // group agents by team
   118→}
   119→```
   120→
   121→**New types** (`src/lib/agent/types.ts`):
   122→```typescript
   123→export interface TeamConfig {
   124→  id: string
   125→  name: string
   126→  mode: OrchestrationMode
   127→  agents: AgentConfig[]
   128→  terminationCondition: TerminationCondition
   129→  maxConcurrency?: number
   130→}
   131→
   132→export type TerminationCondition =
   133→  | { type: 'max_steps'; value: number }
   134→  | { type: 'text_mention'; text: string }
   135→  | { type: 'approval'; requiredFrom: string[] }
   136→  | { type: 'composite'; conditions: TerminationCondition[]; operator: 'and' | 'or' }
   137→```
   138→
   139→**New engine files:**
   140→- `src/lib/agent/orchestrator.ts` — Master orchestrator that selects execution strategy
   141→- `src/lib/agent/strategies/sequential.ts` — Pipeline execution
   142→- `src/lib/agent/strategies/group.ts` — Shared-context turn-taking
   143→- `src/lib/agent/strategies/hierarchical.ts` — Manager-worker delegation
   144→- `src/lib/agent/strategies/parallel.ts` — Fan-out with concurrency control
   145→
   146→**Key design principle (from AutoGen research):** Use **sequential** when steps are fixed and deterministic. Use **group chat** when agents need shared context and iterative collaboration. Replace LLM speaker selection with rules when the order is obvious.
   147→
   148→### 1.2 — Sequential Pipeline Strategy
   149→
   150→**How it works:** Each agent subscribes to its own "topic" (position in pipeline). Output of agent N becomes input of agent N+1. Termination occurs when the last agent emits `APPROVED` or `maxSteps` is reached.
   151→
   152→**Implementation sketch:**
   153→```typescript
   154→// src/lib/agent/strategies/sequential.ts
   155→export async function runSequentialPipeline(
   156→  team: TeamConfig,
   157→  input: string,
   158→  eventEmitter: EventEmitter
   159→): Promise<AgentEvent[]> {
   160→  let currentInput = input;
   161→  const allEvents: AgentEvent[] = [];
   162→
   163→  for (const agent of team.agents) {
   164→    const result = await runSingleAgent(agent, currentInput, eventEmitter);
   165→    allEvents.push(...result.events);
   166→    
   167→    if (result.status === 'failed') break; // Stop pipeline on failure
   168→    currentInput = result.output; // Handoff to next agent
   169→  }
   170→
   171→  return allEvents;
   172→}
   173→```
   174→
   175→**UI impact:** "Execution Strategy" dropdown in sidebar/inspector. Pipeline agents shown connected left-to-right on canvas.
   176→
   177→### 1.3 — Group Chat Strategy
   178→
   179→**How it works:** All agents share a common message history. A Group Chat Manager (LLM-powered or rule-based) selects the next speaker. Termination on `APPROVE`, `TERMINATE`, or `maxMessages`.
   180→
   181→**Implementation sketch:**
   182→```typescript
   183→// src/lib/agent/strategies/group.ts
   184→export async function runGroupChat(
   185→  team: TeamConfig,
   186→  input: string,
   187→  eventEmitter: EventEmitter
   188→): Promise<AgentEvent[]> {
   189→  const sharedHistory: ChatMessage[] = [{ role: 'user', content: input }];
   190→  const allEvents: AgentEvent[] = [];
   191→  let terminated = false;
   192→
   193→  while (!terminated) {
   194→    const nextSpeaker = await selectNextSpeaker(team, sharedHistory);
   195→    const response = await runAgentTurn(nextSpeaker, sharedHistory, eventEmitter);
   196→    sharedHistory.push({ role: 'assistant', content: response, source: nextSpeaker.name });
   197→    
   198→    terminated = checkTermination(sharedHistory, team.terminationCondition);
   199→  }
   200→
   201→  return allEvents;
   202→}
   203→```
   204→
   205→**Speaker selection modes:**
   206→- `llm` — Manager agent uses LLM to pick next speaker (flexible but slower)
   207→- `round_robin` — Fixed rotation (simple, predictable)
   208→- `rule_based` — E.g., "reviewer always speaks after writer" (efficient)
   209→
   210→### 1.4 — Hierarchical Strategy
   211→
   212→**How it works:** A manager/planner agent decomposes the goal, assigns sub-tasks to worker agents, collects results, and synthesizes the final output.
   213→
   214→**Key insight from research:** Pairing a weaker, more delegative planner with a strong solver can outperform using a single top-tier model in both roles — the "combo effect."
   215→
   216→### 1.5 — Parallel Strategy
   217→
   218→**How it works:** Same input dispatched to N agents simultaneously. Results collected and merged. `maxConcurrency` limits simultaneous executions.
   219→
   220→**Implementation:** Use `Promise.allSettled()` with a concurrency pool.

   224→### 1.6 — Reflection Loop System (Evaluator-Optimizer Pattern)
   225→
   226→**Research basis:** The Reflection pattern separates generation and critique into two roles — an Optimizer (Generator) and an Evaluator (Critic) — cycled iteratively. GPT-3.5 jumps from 48.1% to 95.1% on coding benchmarks when wrapped in an agentic refinement loop.
   227→
   228→**Implementation:**
   229→
   230→```typescript
   231→// src/lib/agent/reflection.ts
   232→export interface ReflectionConfig {
   233→  enabled: boolean;
   234→  maxIterations: number;     // Default: 3
   235→  criticRole: string;        // Custom critic system prompt
   236→  approvalCriteria: string;  // E.g., "APPROVED if no security vulnerabilities found"
   237→  requireHumanApproval: boolean; // For high-stakes actions
   238→}
   239→
   240→export async function runReflectionLoop(
   241→  generator: AgentConfig,
   242→  critic: AgentConfig,
   243→  input: string,
   244→  config: ReflectionConfig,
   245→  eventEmitter: EventEmitter
   246→): Promise<ReflectionResult> {
   247→  let iteration = 0;
   248→  let currentOutput = '';
   249→  let approved = false;
   250→
   251→  while (iteration < config.maxIterations && !approved) {
   252→    // Generator produces/revises output
   253→    currentOutput = await runAgentTurn(generator, input, eventEmitter);
   254→    
   255→    // Critic evaluates
   256→    const critique = await runCriticEvaluation(critic, currentOutput, config.approvalCriteria, eventEmitter);
   257→    
   258→    approved = critique.includes('APPROVED');
   259→    if (!approved) {
   260→      // Feed critique back to generator for revision
   261→      input = `Previous output:\n${currentOutput}\n\nCritique:\n${critique}\n\nPlease revise.`;
   262→    }
   263→    
   264→    iteration++;
   265→    eventEmitter.emit('reflection_iteration', { iteration, approved, critique });
   266→  }
   267→
   268→  return { output: currentOutput, iterations: iteration, approved };
   269→}
   270→```
   271→
   272→**Database changes:**
   273→```prisma
   274→model Agent {
   275→  // ... existing fields
   276→  reflectionEnabled   Boolean  @default(false)
   277→  reflectionMaxIter   Int      @default(3)
   278→  reflectionCriteria  String   @default("APPROVED if satisfactory")
   279→}
   280→```
   281→
   282→**UI:** "Self-Improve Output" toggle in inspector. Live iteration log showing critique/fix cycle in run view.

   326→### 2.1 — 3-Tier Memory Layer
   327→
   328→**Research basis:** Agentic systems need memory at multiple levels — short-term working memory, long-term knowledge, and artifact storage. The shift from reactive assistants to autonomous workflows is built on external tools and memory rather than prompt-only reasoning.
   329→
   330→**Architecture:**
   331→
   332→| Tier | Scope | Storage | Lifecycle |
   333→|------|-------|---------|-----------|
   334→| **Session** | Current run | In-memory Map | Cleared when run ends |
   335→| **Persistent** | Across runs | SQLite (new model) | Survives restarts |
   336→| **Artifacts** | Files, code, outputs | SQLite + filesystem | Versioned, retrievable |
   337→
   338→**Database changes:**
   339→```prisma
   340→model AgentMemory {
   341→  id        String   @id @default(cuid())
   342→  agentId   String
   343→  agent     Agent    @relation(fields: [agentId], references: [id], onDelete: Cascade)
   344→  key       String   // e.g., "user_preference", "project_context"
   345→  value     String   // JSON string
   346→  tier      String   @default("persistent") // session | persistent | artifact
   347→  runId     String?  // Null for persistent, set for session
   348→  createdAt DateTime @default(now())
   349→  updatedAt DateTime @updatedAt
   350→
   351→  @@unique([agentId, key, tier])
   352→}
   353→
   354→model Artifact {
   355→  id        String   @id @default(cuid())
   356→  agentId   String
   357→  agent     Agent    @relation(fields: [agentId], references: [id], onDelete: Cascade)
   358→  runId     String?
   359→  name      String
   360→  type      String   // code | text | json | markdown | file
   361→  content   String   // The actual content
   362→  metadata  String?  // JSON: size, language, version, etc.
   363→  createdAt DateTime @default(now())
   364→}
   365→```
   366→
   367→**New engine file:** `src/lib/agent/memory-v2.ts`
   368→```typescript
   369→export interface MemoryStore {

   466→## Phase 3: Governance, Safety & Observability
   467→
   468→### 3.1 — Policy & Approval System
   469→
   470→**Research basis:** Multi-agent systems introduce confused-deputy attacks and cross-agent privilege escalation. SEAgent uses Mandatory Access Control with Block/Deny, User Prompt/Ask, and Shadow Mode outcomes. AWS and Microsoft both mandate least-privilege access, sandboxed execution, and immutable audit logs.
   471→
   472→**Architecture:**
   473→
   474→```typescript
   475→// src/lib/agent/policy.ts
   476→export type RiskLevel = 'low' | 'medium' | 'high';
   477→
   478→export interface PolicyRule {
   479→  id: string;
   480→  name: string;
   481→  description: string;
   482→  condition: {
   483→    tool?: string[];        // Which tools this applies to
   484→    role?: AgentRole[];     // Which roles
   485→    riskLevel?: RiskLevel;  // Which risk levels
   486→  };
   487→  action: 'allow' | 'block' | 'ask_user' | 'shadow';
   488→  reason: string;
   489→}
   490→
   491→export interface ApprovalRequest {
   492→  id: string;
   493→  runId: string;
   494→  agentId: string;
   495→  stepId: string;
   496→  tool: string;
   497→  input: string;
   498→  riskLevel: RiskLevel;
   499→  status: 'pending' | 'approved' | 'denied' | 'expired';
   500→  requestedAt: Date;
   501→  respondedAt?: Date;
   502→  respondedBy?: string;
   503→  reason?: string;
   504→}
   505→```
   506→
   507→**Default policies:**
   508→| Action | Risk | Policy |
   509→|--------|------|--------|
   510→| `search` (read-only) | Low | `allow` |
   511→| `write` (create artifact) | Medium | `ask_user` |
   512→| `code` (execute code) | High | `ask_user` |
   513→| `browser` (external request) | Medium | `allow` with logging |
   514→| Any action by `reviewer` role | Low | `allow` (read-only role) |
   515→
   516→**Database:**
   517→```prisma
   518→model PolicyRule {
   519→  id          String   @id @default(cuid())
   520→  name        String
   521→  description String?
   522→  condition   String   // JSON
   523→  action      String   // allow | block | ask_user | shadow
   524→  priority    Int      @default(0)  // Higher = evaluated first
   525→  enabled     Boolean  @default(true)
   526→  createdAt   DateTime @default(now())
   527→  updatedAt   DateTime @updatedAt
   528→}
   529→
   530→model ApprovalRequest {
   531→  id            String   @id @default(cuid())
   532→  runId         String
   533→  agentId       String
   534→  stepId        String
   535→  tool          String
   536→  input         String
   537→  riskLevel     String   // low | medium | high
   538→  status        String   @default("pending") // pending | approved | denied | expired
   539→  requestedAt   DateTime @default(now())
   540→  respondedAt   DateTime?
   541→  respondedBy   String?
   542→  reason        String?
   543→}
   544→```
   545→
   546→**API routes:**
   547→- `GET /api/policy/list` — List all policies
   548→- `POST /api/policy/create` — Create a policy rule
   549→- `PATCH /api/policy/update` — Update a policy
   550→- `DELETE /api/policy/delete` — Delete a policy
   551→- `GET /api/approval/pending` — List pending approval requests
   552→- `POST /api/approval/respond` — Approve or deny a request
   553→
   554→**UI:**

   559→### 3.2 — Audit Trail (Immutable)
   560→
   561→**Database:**
   562→```prisma
   563→model AuditLog {

   680→### 4.2 — Parallel + Async Engine
   681→
   682→**Implementation:**
   683→```typescript
   684→// src/lib/agent/concurrency.ts
   685→export async function runWithConcurrency<T>(
   686→  tasks: (() => Promise<T>)[],
   687→  maxConcurrency: number
   688→): Promise<PromiseSettledResult<T>[]> {
   689→  const results: PromiseSettledResult<T>[] = [];
   690→  const executing: Promise<void>[] = [];
   691→
   692→  for (const task of tasks) {
   693→    const p = task().then(result => {
   694→      results.push({ status: 'fulfilled', value: result });
   695→    }, error => {
   696→      results.push({ status: 'rejected', reason: error });
   697→    });
   698→
   699→    executing.push(p);
   700→
   701→    if (executing.length >= maxConcurrency) {
   702→      await Promise.race(executing);
   703→      executing.splice(
   704→        executing.findIndex(e => e === p),
   705→        1
   706→      );
   707→    }
   708→  }
   709→
   710→  await Promise.all(executing);
   711→  return results;
   712→}
   713→```

   873→## Risk Analysis
   874→
   875→### Technical Risks
   876→
   877→| Risk | Likelihood | Impact | Mitigation |
   878→|------|-----------|--------|------------|
   879→| SSE breaks with multi-agent (event ordering) | Medium | High | Use structured event types with agentId + sequence numbers |
   880→| SQLite can't handle concurrent writes from parallel agents | Medium | High | Use WAL mode; consider migration path to Postgres for scale |
   881→| LLM costs spike with reflection loops + multi-agent | High | Medium | Add token budget per run; cap reflection iterations; cache planner decisions |
   882→| Group chat context bloat degrades agent quality | Medium | Medium | Implement context windowing; summarize older messages |
   883→| Kill switch doesn't cleanly stop parallel agents | Medium | High | Use AbortController per agent; propagate cancellation signals |
   884→
   885→### Security Risks (from Research)
   886→
   887→| Risk | Description | Mitigation |
   888→|------|-------------|------------|
   889→| **Confused Deputy** | Untrusted agent manipulates trusted agent into privileged action | Policy engine checks inter-agent messages; role-based permission boundaries |
   890→| **Cross-Agent Escalation** | Agents combine permissions to exceed individual authority | Least-privilege per role; audit all cross-agent communication |
   891→| **Prompt Injection via Tool Output** | Malicious tool output hijacks agent reasoning | Sanitize tool outputs; separate instructions from data in prompts |
   892→| **Reward Hacking** (reflection loops) | Generator learns to produce outputs that fool the critic, not genuinely better ones | Use deterministic validators where possible; cap iterations; require human approval for high-stakes |

   917→## Key Research-Informed Design Decisions
   918→
   919→1. **Sequential over Group Chat as default** — Research shows sequential is cleaner for enterprise pipelines. Group chat adds value only when shared deliberation is needed (writer-editor cycles).
   920→
   921→2. **Deterministic validators over LLM judges** — Inspired by RLVR (Reinforcement Learning with Verifiable Rewards), which outperforms Process Reward Models because deterministic checks (JSON parsing, code compilation) are immune to reward hacking.
   922→
   923→3. **Soft limits over hard kills** — AgentCgroup research shows that OOM kills destroy non-recoverable LLM context. Our policy engine should throttle/pause rather than terminate when possible.
   924→
   925→4. **Rule-based speaker selection over LLM** — AutoGen docs recommend replacing LLM speaker selection with simple rules when the order is obvious. This saves tokens and latency.
   926→
   927→5. **Weaker planner + stronger solver** — The "combo effect" shows that a delegative planner paired with a capable solver outperforms a single dominant model trying to do everything.
   928→
   929→6. **Immutable audit trail** — Both AWS and Microsoft security guidance mandate traceability as a core design requirement, not an optional add-on.
   930→
   931→7. **Approval gates for high-risk actions** — SEAgent's three-outcome model (Block/Ask/Shadow) maps directly to our policy engine's allow/block/ask_user/shadow actions.
