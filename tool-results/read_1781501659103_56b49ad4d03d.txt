    33→    33→01   EXECUTIVE SUMMARY
    34→    34→Hermes is no longer a “workflow engine” project. It is evolving into a deterministic runtime platform, with agent execution as
    35→    35→merely one application layer built on top of a proven kernel. This document defines the phased engineering roadmap from
    36→    36→kernel validation through to distributed multi-node federation.
    37→    37→The roadmap comprises seven phases (Phase 0 through Phase 6), each with explicit objectives, deliverables, execution flows,
    38→    38→and success criteria. The strategic foundation of the entire platform rests on Phase 0: proving that Hermes can deterministically
    39→    39→reconstruct reality from facts. Everything else is built on top of that kernel.
    40→    40→⚠ STRATEGIC PRIORITY
    41→    41→No subsequent phase may begin until Phase 0 success criteria are fully demonstrated. The deterministic kernel is the
    42→    42→non-negotiable foundation of the entire platform.
    43→    43→02   STRATEGIC CONTEXT
    44→    44→The core architectural thesis of Hermes is this: most agent frameworks begin by building agents, then attempt to retrofit
    45→    45→governance, observability, and determinism. Hermes inverts this. The deterministic kernel is built first. Governance is built
    46→    46→second. Agents are introduced only after the substrate beneath them is proven correct and mature.
    47→    47→The strategic inflection point is between Phase 0 and Phase 1. Once the event stream → deterministic replay → identical state
    48→    48→reconstruction chain is validated, the hardest and most differentiated part of the platform is complete. All subsequent phases
    49→    49→add capabilities around a proven kernel, rather than discovering the kernel while simultaneously building agents, UIs,
    50→    50→orchestration, and governance.

   274→   274→1. ABSTRACT
   275→   275→This RFC defines the Hermes Runtime as a deterministic, replayable state machine governed by a strict hierarchy of compiled
   276→   276→intermediate representations, anchored by an executable constitution.
   277→   277→The runtime treats LLMs as proposal generators. All actions are filtered through synchronous policy evaluation, executed as
   278→   278→side-effects, and recorded as causal facts. The kernel reducer derives reality exclusively from state-transition facts
   279→   279→(SystemEvent), which must provably trace their origin to execution attempts (ExecutionEvent).
   280→   280→This RFC formalizes:
   281→   281→An executable ConstitutionIR with strict precedence and severity.
   282→   282→Causal closure between execution attempts and state transitions.
   283→   283→A primitive, explicitly typed state-transition taxonomy.
   284→   284→An event-sourced blackboard projection model.
   285→   285→Cryptographic authorship via signatures.
   286→   286→The TraceManifest as the genesis block of execution.
   287→   287→2. GOALS
   288→   288→The Hermes Runtime exists to support workflows that are:
   289→   289→Deterministic under replay with bounded recovery
   290→   290→Causally closed (no orphaned state mutations)
   291→   291→Constitutionally supreme and policy-governed
   292→   292→Auditable with full provenance and cryptographic authorship
   293→   293→Robust to probabilistic model output, retries, and partial failure

   307→   307→3. TERMINOLOGY
   308→   308→TERM
   309→   309→DEFINITION
   310→   310→ConstitutionIR
   311→   311→The runtime-wide axiomatic law. Compiled into executable validators. Overrides all other IRs.
   312→   312→TraceManifest
   313→   313→The genesis block of a trace. Binds a traceId to its specific Constitution, Plan, and Policy hashes.
   314→   314→Causal Closure
   315→   315→The invariant that every state-mutating SystemEvent must reference the ExecutionEvent or DecisionEvent
   316→   316→that caused it, eliminating trust in rootless state transitions.
   317→   317→Event-Sourced
   318→   318→Blackboard
   319→   319→A memory substrate where state is a projection of BLACKBOARD_WRITTEN system events, rather than
   320→   320→an opaque mutated object.
   321→   321→Signature
   322→   322→A cryptographic attestation of authorship, binding an identity to an artifact or event.
   323→   323→4. ARCHITECTURAL INVARIANTS
   324→   324→4.1 Factual Reduction: The reducer consumes only SystemEvents. No other event tier may directly mutate kernel state.
   325→   325→4.2 Causal Closure: Every SystemEvent representing a step or workflow transition must reference the executionEventId or
   326→   326→decisionEventId that precipitated it. Rootless state transitions are constitutionally invalid.
   327→   327→4.3 Constitutional Supremacy: IR precedence is strictly enforced. Conflict at any level results in an immediate
   328→   328→FATAL_CONSTITUTIONAL_VIOLATION.
   329→   329→ConstitutionIR > PolicyIR > ExecIR > HermesIR
   330→   330→4.4 Single Authoritative Sequencer (Model A): To guarantee strict deterministic replay, the runtime operates on a single-
   331→   331→authoritative-event-sequencer model. eventSequence and logicalClock are sufficient. Vector clocks are excluded from the
   332→   332→kernel; distributed execution is achieved by delegating to isolated sub-traces or external workers whose results are normalized
   333→   333→back into the authoritative sequence.
   334→   334→4.5 Event-Sourced Memory: Blackboard state is derived by folding BLACKBOARD_WRITTEN events. In-place mutation
   335→   335→outside the event stream is prohibited.
   336→   336→4.6 Authorship over Integrity: Hashes prove integrity; signatures prove authority. Governance proposals, approvals, and
   337→   337→constitutional amendments require cryptographic signatures.
   338→   338→5. CANONICAL IR MODEL & PRECEDENCE
   339→   339→5.1 ConstitutionIR
   340→   340→Defines runtime-wide executable axioms. The ConstitutionIR is the supreme governing artifact of a trace. All validators
   341→   341→compiled from it run synchronously prior to any policy or execution evaluation.
   342→   342→interface ConstitutionIR {
   343→   343→  id: string;
   344→   344→  version: string;
   345→   345→  constitutionalHash: string;
   346→   346→  axioms: ConstitutionalAxiom[];
   347→   347→}
   348→   348→interface ConstitutionalAxiom {
   349→   349→  id: string;
   350→   350→  description: string;
   351→   351→  severity: 'FATAL' | 'ERROR' | 'WARNING';
   352→   352→  validator: string; // URI or hash of a deterministic validation function
   353→   353→}
   354→   354→
   355→   355→--- Page 8 ---
   356→   356→Example Axiom (Severity: FATAL): "No STEP_SUCCEEDED event is valid without a preceding ExecutionEvent referencing the
   357→   357→same stepId."
   358→   358→5.2 HermesIR (Intent), ExecIR (Mechanics), PolicyIR (Law)
   359→   359→As defined in v1.3, but strictly subordinate to ConstitutionIR. These IRs govern intent expression, execution mechanics, and
   360→   360→runtime law respectively. No construct within these IRs may supersede or conflict with a constitutional axiom. Violations are
   361→   361→surfaced as FATAL_CONSTITUTIONAL_VIOLATION kernel halts per Invariant 4.3.
   362→   362→6. TRACEMANIFEST (GENESIS BLOCK)
   363→   363→Before execution begins, a trace must be instantiated with its constitutional and operational anchors. The TraceManifest is the
   364→   364→first artifact written and is immutable for the lifetime of the trace.
   365→   365→interface TraceManifest {
   366→   366→  traceId: string;
   367→   367→  planId: string;
   368→   368→  constitutionHash: string;
   369→   369→  executionPlanHash: string;
   370→   370→  policyHash: string;
   371→   371→  initiatedBy: Signature;
   372→   372→  createdAt: number;
   373→   373→}
   374→   374→Replay validation begins by loading the TraceManifest to verify that subsequent events adhere to the correct constitution and
   375→   375→plans. Any mismatch between the manifest hashes and the artifacts available at replay time constitutes a fatal integrity
   376→   376→violation.
   377→   377→7. KERNEL STATE & EVENT-SOURCED BLACKBOARD

   402→   402→8. EVENT TAXONOMY & CAUSAL LINKING
   403→   403→Events are strictly tiered. Only SystemEvents are valid reducer inputs. SystemAction values are an explicit, closed set of
   404→   404→primitives — no generic details blobs are permitted at the type level.
   405→   405→8.1 Base Event
   406→   406→All events in the Hermes Runtime extend BaseEvent. The cryptographic chain linkage (eventHash / previousEventHash)
   407→   407→enables tamper detection across the full trace.
   408→   408→interface BaseEvent {
   409→   409→  eventId: string;
   410→   410→  traceId: string;
   411→   411→  eventSequence: number;
   412→   412→  causationId: string | null;
   413→   413→  correlationId: string;
   414→   414→  tier: EventTier;
   415→   415→  timestamp: number;
   416→   416→  logicalClock: number;
   417→   417→  eventHash: string;
   418→   418→  previousEventHash: string | null;
   419→   419→  signatures?: Signature[]; // Required for governance/approval events
   420→   420→}
   421→   421→8.2 SystemEvent (The Only Reducer Input)
   422→   422→State transitions are primitive and explicit. No generic details blobs at the type boundary. Each SystemAction has a strictly
   423→   423→typed payload schema in the implementation layer.
   424→   424→type SystemAction =
   425→   425→  | 'WORKFLOW_INITIALIZED' | 'WORKFLOW_BLOCKED' | 'WORKFLOW_FAILED' | 'WORKFLOW_COMPLETED'
   426→   426→  | 'STEP_STARTED' | 'STEP_SUCCEEDED' | 'STEP_FAILED'
   427→   427→  | 'BLACKBOARD_WRITTEN' | 'BLACKBOARD_CLEARED'
   428→   428→  | 'POLICY_VIOLATION' | 'CHECKPOINT_REACHED';
   429→   429→interface SystemEvent extends BaseEvent {
   430→   430→  tier: 'SYSTEM';
   431→   431→  payload: {
   432→   432→    action: SystemAction;
   433→   433→    // Causal closure: The event that authorized this state mutation
   434→   434→    executionEventId?: string; // Required for STEP_SUCCEEDED/FAILED
   435→   435→    decisionEventId?: string;  // Required for STEP_STARTED
   436→   436→    details?: Record<string, unknown>; // Strictly typed per action in implementation
   437→   437→  };
   438→   438→}
   439→   439→
   440→   440→--- Page 10 ---
   441→   441→8.3 ExecutionEvent
   442→   442→Records the factual result of a side-effect boundary. An ExecutionEvent is the ground truth of what occurred at a tool
   443→   443→invocation. It is the mandatory antecedent of any STEP_SUCCEEDED or STEP_FAILED system event.
   444→   444→interface ExecutionEvent extends BaseEvent {
   445→   445→  tier: 'EXECUTION';
   446→   446→  payload: {
   447→   447→    toolId: string;
   448→   448→    invocationId: string;
   449→   449→    inputs: unknown;
   450→   450→    outputs: unknown;
   451→   451→    status: 'SUCCESS' | 'FAILURE';
   452→   452→  };
   453→   453→}
   454→   454→9. SIGNATURE MODEL
   455→   455→Integrity (hashes) prevents tampering. Signatures establish authority. These are orthogonal concerns: a valid hash on a
   456→   456→fraudulent artifact is meaningless without a corresponding valid signature from an authorized identity.
   457→   457→interface Signature {
   458→   458→  signerId: string;
   459→   459→  algorithm: string;
   460→   460→  value: string; // Cryptographic signature over the artifact hash
   461→   461→  timestamp: number;
   462→   462→}
   463→   463→Signature requirements:
   464→   464→GovernanceProposal must be signed by the proposing Council Agent.
   465→   465→REQUIRE_APPROVAL outcomes must be resolved via a signed DecisionEvent from an authorized human or system.
   466→   466→ConstitutionIR amendments require quorum signatures.
   467→   467→10. POLICY & CONSTITUTIONAL EVALUATION
   468→   468→10.1 Precedence Evaluation Flow
   469→   469→When a DecisionEvent occurs, the following evaluation sequence is strictly enforced in order:
   470→   470→Constitutional Check: Does the decision violate a ConstitutionIR axiom? 
   471→   471→Yes (FATAL): Halt kernel. Emit FATAL_CONSTITUTIONAL_VIOLATION.
   472→   472→Yes (ERROR/WARNING): Emit violation event, proceed or block based on severity logic.
   473→   473→Policy Check: Does PolicyIR permit the execution? 
   474→   474→DENY: Emit POLICY_VIOLATION, transition step to FAILED.
   475→   475→REQUIRE_APPROVAL: Pause until signed approval DecisionEvent arrives.
   476→   476→ALLOW / CONSTRAINED_ALLOW: Proceed to ExecutionBoundary.
   477→   477→PURITY INVARIANT
   478→   478→Both Constitution and Policy evaluation must remain pure, deterministic, network-isolated, and side-effect free. Any
   479→   479→evaluator that performs I/O, network access, or non-deterministic computation is constitutionally invalid and must be
   480→   480→rejected at load time.
